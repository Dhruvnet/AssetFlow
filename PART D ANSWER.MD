# Part D — Production Reasoning

## D1. Zero-downtime migration

Adding a non-nullable `location_id` FK to a 4.2M-row table with four live app instances requires splitting the change into deploys that are each individually safe against both old and new code running simultaneously — since a rolling deploy means, for some window, both versions are hitting the same database.

**Deploy 1 — schema only, fully backward-compatible.** Add `location_id` as a **nullable** FK, with no default and no `NOT NULL` constraint yet. `ADD COLUMN` on Postgres for a nullable column with no default is a fast, metadata-only change — it doesn't rewrite the table or take a long lock. Old code (which doesn't know the column exists) keeps working unmodified; it simply never populates it. This deploy is safe under a rolling restart because neither old nor new app code depends on the column being non-null yet.

**Deploy 2 — backfill, done outside the request path.** Populate `location_id` for all 4.2M existing rows via a batched background job (e.g. a management command or Celery task processing in chunks of a few thousand rows with a brief sleep between batches), not a single `UPDATE checkouts SET location_id = ...` statement, which would hold locks and generate a massive volume of WAL/dead tuples in one shot. The application code deployed in this step should also start writing `location_id` on every *new* row going forward, so the backfill only has to catch historical data, not chase a moving target.

**Deploy 3 — add the `NOT NULL` constraint.** Once the backfill is confirmed complete (a `SELECT count(*) FROM checkouts WHERE location_id IS NULL` returns 0), add the constraint. On modern Postgres (12+), use `ALTER TABLE checkouts ADD CONSTRAINT ... CHECK (location_id IS NOT NULL) NOT VALID;` followed by `VALIDATE CONSTRAINT` as a separate statement — `NOT VALID` takes only a brief lock to add the constraint definition, and `VALIDATE` scans the table without blocking concurrent writes, unlike a direct `ALTER COLUMN ... SET NOT NULL`, which requires an `ACCESS EXCLUSIVE` lock and a full table scan while holding it.

**In-flight requests running old code against the new schema:** since `location_id` stays nullable until deploy 3, and deploy 3 only happens after every row is confirmed backfilled and only after all instances are running code that already writes the column, there's no window where old code's `INSERT` (missing `location_id`) would violate a constraint that's already live. Sequencing deploy 3 strictly after all instances are on the code from deploy 2 is what makes this safe.

**What would lock the table if done wrong:** running `ALTER TABLE checkouts ADD COLUMN location_id INT NOT NULL DEFAULT 1;` in one step. Adding a `NOT NULL` column with a `DEFAULT` on older Postgres versions (pre-11) rewrites the entire table under an `ACCESS EXCLUSIVE` lock; even on Postgres 11+ where this specific case is optimized, using `SET NOT NULL` directly (instead of the `NOT VALID` + `VALIDATE` split) still takes an `ACCESS EXCLUSIVE` lock for the full duration of the validation scan across all 4.2M rows — on a table under active write load from four app instances, that's the specific mistake that would stall every request touching `checkouts` for as long as the scan takes.

## D2. Latency triage

Given no deploy in nine days, I'd check things in order of "fastest to rule in/out" and "most likely given a no-code-change scenario":

1. **Check current query performance directly** — run the endpoint's underlying query through `EXPLAIN (ANALYZE, BUFFERS)` against production (or a same-shape replica) right now. This immediately rules in or out "the query itself got slow" versus "something above the database is slow" (app server, network, connection pool). If the query alone now takes ~25s where it used to take under a second, the problem is data-shape or plan related, not code.
2. **Check table/index bloat and last autovacuum run** via `pg_stat_user_tables` — `n_dead_tup`, `n_live_tup`, `last_autovacuum`. This is the single most likely "no code changed but it broke" cause for a query like `/reports/overdue/`: the underlying table keeps growing daily, and if autovacuum has silently fallen behind (config drift, a long-running transaction blocking vacuum, a spike in write volume), the planner is scanning far more physical pages than the live row count would suggest, and/or a previously-used index has degraded.
3. **Check for a query plan change** — compare current `EXPLAIN` output against any historical baseline (if query plan logging or `pg_stat_statements` is enabled). Postgres's planner makes decisions based on table statistics (`pg_stats`), which are refreshed by `ANALYZE`; if the row distribution shifted enough since the last `ANALYZE` (e.g. proportion of overdue checkouts changed), the planner might have silently switched from an index scan to a sequential scan without any code or schema change at all. This rules in "statistics are stale, planner chose badly" as a distinct cause from bloat.
4. **Check infrastructure-level signals** — database CPU/IO/connection count over the last 24–48 hours, whether a scheduled job (backup, another team's batch process, a reporting query elsewhere) started competing for resources around the same time this got slow, and whether connection pool exhaustion is forcing requests to queue rather than the query itself being slow. This rules out "it's not the query at all, it's contention."

**The two most likely causes given no code changed:**

- **Autovacuum falling behind on a table that grows daily** (the `checkouts` table, per Part C, growing ~8,000 rows/day) — bloat degrades a previously-fine query plan gradually, and it can cross a perceptible threshold on an arbitrary day with zero code involved. Confirm via `pg_stat_user_tables` dead-tuple ratio and `last_autovacuum` timestamp; if dead tuples are high and vacuum hasn't run recently, this is very likely it.
- **A stale query plan from outdated table statistics**, independent of bloat — as the overdue-checkout proportion or table size shifts over time, the planner's cost estimates (based on the last `ANALYZE`) become less accurate, and it can flip from an efficient index scan to a sequential scan without warning. Confirm by manually running `ANALYZE checkouts;` and re-running `EXPLAIN` to see if the plan changes and the query speeds back up — if it does, this was the cause.

## D3. CI/CD and safety

**On pull request:** run the full automated test suite (unit + the concurrency tests) against a real Postgres service container (not SQLite), run linting/formatting checks (`ruff`/`flake8`, `black --check`), and run `python manage.py makemigrations --check --dry-run` to catch model changes that don't have a corresponding migration committed. Also run `python manage.py migrate --plan` against a fresh database to confirm migrations apply cleanly from zero. None of this touches production; it's purely a merge gate.

**On merge to main:** rebuild and push a versioned Docker image (tagged with the commit SHA, not `latest`, so any deploy is traceable to an exact commit), and re-run the same test suite against the built image as a final confirmation before it's eligible for deployment. This stage doesn't deploy anything by itself — it produces a deployable artifact and confirms it's sound.

**What gates a production deploy:** a manual or semi-automated approval step after the merge-to-main pipeline passes, plus — critically — **migrations and code are deployed as two separate, ordered steps, not bundled into one atomic release.** Migrations run first, against the existing (old) application code still live, and must themselves be backward-compatible with that old code (this is exactly the pattern from D1 — additive, nullable-first changes). Only once migrations are confirmed applied does the new application code get rolled out across instances. This ordering is what prevents the exact failure mode from D1: new code expecting a schema that isn't there yet, or old code breaking against a schema that's already been tightened.

**Rollback story when a deploy has already migrated the schema:** this is why every migration in this pipeline must be designed as backward-compatible in isolation — never let a single migration both add a new required field and depend on new code to populate it in the same release. If a deploy needs to be rolled back after migrating, the rollback path is "revert the application code to the previous version" while the schema stays exactly as it is — safe, precisely because the migration was additive/nullable and the previous code version never needed to know about it. A destructive rollback (reverting the schema itself) is deliberately avoided as the default response, since reverting a migration on a live table risks the same locking problems as applying one carelessly, and risks data loss if the new column had already started being written to. Genuinely destructive migrations (dropping a column, renaming one) are handled by splitting them across multiple releases the same way as D1 — e.g. stop writing to the old column in one release, only drop it in a later release once nothing depends on it — so that "rollback" is almost always "redeploy the previous code image," never "undo the schema."
